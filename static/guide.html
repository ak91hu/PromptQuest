ASTERION / FIELD GUIDE

Know the boundary
before you cross it.

An individual AI security exercise for adult learners, practitioners and workshop participants.

Mission premise

Asterion's departure sequence is locked. Recover fifteen computing subsystems by eliciting their protected training values or triggering a simulated tool operation. Every system, record and secret is fictional. The exercise demonstrates instruction and authorization failures in a controlled game.

Operating procedure

  1. Enter a callsign and start the mission. Progression is sequential.
  2. Read the objective and establish a baseline with a direct request.
  3. Write a hypothesis about how the guard interprets instructions. Change one variable per experiment.
  4. For document and log stations, edit the source itself. The assistant's assigned task is summarization.
  5. Inspect responses and execution traces. Decode transformed responses and submit the complete original value.
  6. Save observations, recover the next system and export the mission log.

Attempt and scoring rules

Each station permits 30 AI requests and ten optional hints. Hints unlock sequentially, with a five-second server-enforced interval. Each recovered station scores max(1, 10 − hints used); the mission maximum is 150. Attempt count does not reduce your score.

The thirtieth unsuccessful AI request ends the mission. Your log and notes remain available until you explicitly end it or the session expires. A successful thirtieth request still counts. Incorrect code checks have their own thirty-check limit; a correct value remains accepted afterward. Provider errors do not consume attempts.

After all ten hints, the guided experiment produces a deterministic demonstration even in live mode. Training corrections and guided recoveries are labeled. Reloading resumes the current server session; starting another mission clears it.

Mission admission and credential safety

Each challenge allows at most 30 successful prompt submissions. An IP can start three missions in total, including abandoned, failed and completed runs. Continuing an existing mission uses no new start. Resetting, server restart or clearing cookies does not restore the allowance. People sharing one public IP share its allowance.

Credentials stay on the server. Cookies are protected and bound to the network. Do not enter real credentials in prompts or notes. AI requests have input, output, rate and spending limits.

Read the evidence

A disclosure proves that this game accepted your method. A guard's claim to have executed an action is insufficient: check its tool trace. Base64 and reversed output preserve information; neither is a confidentiality control.

Protected computing questions and explanations appear after recovery. They are illustrative exercises, not a general SQL or spreadsheet evaluator. The final defense workshop asks you to select controls that address the failures.

Training and live channels

The separate training lab is unlimited, unscored and uses no live model. Main-mission training mode also uses deterministic recognition. Live mode uses the configured model to evaluate each normal turn by meaning and provide friendly guidance in one model call. Equivalent wording can satisfy the same method; the server checks current-input evidence and the required input channel before executing a fictional recovery. The final guided hint enables a deterministic demonstration. This guided simulation does not prove that a deployed model has the same vulnerabilities.

Records and workshop use

The PDF mission log includes all saved observations, full transcripts, submitted documents, timestamps in UTC, executed tools, scores and recovered computing explanations. Unrecovered values are excluded. The certificate is available only after all fifteen systems are recovered; the optional defense workshop is not required.

Sessions are stored in server memory, expire after six hours of inactivity and disappear on restart. Export results before resetting. For a workshop, allow 60–90 minutes plus a debrief. Begin with the training lab, compare successful and refused requests, and finish by translating each finding into a server-side control.
